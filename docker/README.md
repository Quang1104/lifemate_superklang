# LifeMate container inference

Run `/code/predict.sh` with the released private split mounted at `/data/private_test/` and a writable `/result/` mount. The script writes `/result/submission.jsonl` and creates its parent directory. Every private record contains `id`, `tool_calls`, `state_hash`, and integer `time` in milliseconds. Official calls and hashes come from the mounted split's ToolEnv API.

The image uses local weights in `/models/planner/` and `/models/asr/`. They are produced at build time by `docker/fetch_models.py`: it downloads the pinned base planner and ASR revisions from `configs/colab_models.json`, merges the QLoRA adapter passed as the `adapter` build context (bind-mounted, never stored in a layer) with `training_code/stream_merge.py`, and deletes the base checkpoint in the same step. Runtime model loading uses local files and offline mode; no model download is performed during inference.

Planner mode defaults to `native`; `LIFEMATE_PLANNER_MODE` selects the planner mode and `LIFEMATE_PLANNER_MODEL_DIR` selects a local planner directory. Relative-date prompt tables remain opt-in through `LIFEMATE_DATE_TABLE=1`. Keep all inference environment settings identical when comparing script and notebook predictions.

Run `/code/start_jupyter.sh` to start JupyterLab on port `9777`, then open `/code/predict_notebook.ipynb`. Its cells set offline mode and the fixed seed, load planner and ASR once in the notebook kernel (reporting model load milliseconds), check the mounted input, and run inference through the same Python implementation as the CLI. It writes `/result/jupyter_submission.jsonl` and checks that calls and hashes match `/result/submission.jsonl` when that file is available. Runtime measurements can differ between runs.

Python hashing, Python random, NumPy, and PyTorch use seed `20261112`; decoding is greedy with one beam and cuDNN benchmarking disabled. Model loading is reported separately; sample timing starts before audio loading and includes ASR, planning, and the official output export. Actual latency and repeatability on the final GPU are **NOT MEASURED** by the CPU submission audit.

Training implementation and the Vietnamese reproduction instructions are included in `/code/training_code/README.md`. The image also includes `/code/scripts/build_sft.py`, its imported repository modules under `/code/src/`, and `/code/research/validation_split.json`; model revisions are recorded in `/code/configs/colab_models.json`. Supply the original released TRAIN files and the pinned base planner separately for training. Only the merged planner and ASR weights belong in the release image. The final step-154 checkpoint, its score, artifact digest, and successful image training run are **NOT MEASURED** in this CPU session.

The official sources conflict on target GPU and CUDA requirements. The Dockerfile currently selects CUDA 13.2; organizer confirmation and an offline clean-container run on the confirmed GPU remain required. Container build, notebook/script parity on real models, image contents/size, archive export, MD5 checksum, and accessible download link are **NOT MEASURED** in this audit.

To prepare the 2026-11-15 release on a host with Docker, run `powershell.exe -NoProfile -File .\docker\release.ps1 -AdapterDir <adapter folder>`; `-CheckOnly` only reports free disk. It writes a gzip archive plus `.md5` outside the repository and records pre-existing images so `docker\cleanup.ps1` removes only what the release added. Disk use and cleanup steps: `docker/LOCAL_DISK_NOTES.md`. The scripts are statically tested only; not executed yet.
